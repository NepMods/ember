Development Setup

Prerequisites

  • Go 1.21+ (the module uses go 1.26 — any recent version works)
  • Git for version control
  • SQLite3 (development headers for mattn/go-sqlite3)
  • Optionally, PostgreSQL and MySQL for dialect-specific manual testing

Quick Start

git clone https://github.com/NepMods/ember.git
cd ember
go mod download
go test -v -count=1 ./...

Recommended Tools

  • golangci-lint — run golangci-lint run ./... for comprehensive linting
  • go vet — always run before committing
  • staticcheck — additional static analysis
  • delve — debugger for stepping through complex issues

Running Tests

Full Test Suite

go test -v -count=1 -race ./...

Run Specific Tests

# Run a specific test function
go test -v -run TestBuilderToSQL_Select

# Run all model tests
go test -v -run 'TestModel'

# Run all relation/eager loading tests
go test -v -run 'TestEager|TestWith|TestRelation'

# Run with race detector
go test -race -count=1 ./...

Test Coverage

go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out

Test Guidelines

  • All tests use SQLite in-memory (:memory:) — zero setup, fast, deterministic.
  • Write tests in the ember_test package (external) to ensure the public API is exercised as a real consumer would.
  • For dialect-specific behavior, test via ToSQL() output comparison rather than connecting to each database.
  • Use t.Parallel() where appropriate, but be aware that ParseSchema cache and global macro state are shared.
  • New features require new test cases. Bug fixes require a regression test.

Coding Standards

Go Style

  • Run gofmt -s (or go fmt ./...) on all Go code. The CI pipeline enforces this.
  • Follow the Effective Go guidelines.
  • Use golangci-lint defaults — no exceptions without a comment explaining why.
  • Avoid init() functions. Use explicit initialization instead.
  • Prefer table-driven tests with t.Run() subtests.

Naming Conventions

  • Exported symbols use PascalCase. Unexported symbols use camelCase.
  • Acronyms are all-uppercase: ParseSQL, ToJSON, NewDB.
  • Single-letter variable names are acceptable only in short-lived scopes (loop indices, temp values).
  • Error variables are prefixed with Err: ErrNotFound, ErrInvalidModel.
  • Interface names end in -er where conventional: Tabler.

API Design Principles

  • Flat package — No sub-packages. Everything lives in ember.
  • Fluent chaining — Mutator methods return *Builder for chaining.
  • Context-first — All database operations take context.Context as the first argument.
  • Error returns — Methods return errors rather than panicking. Panics are reserved for programmer mistakes.
  • Minimal dependencies — The only external dependency is mattn/go-sqlite3. New dependencies require discussion.

Documentation

  • Every exported symbol must have a Go doc comment.
  • Doc comments should be complete sentences: "ParseSchema parses a Go struct..." not "ParseSchema parses..."
  • Use //nolint comments sparingly and only with a brief justification.
  • Update Project.md when adding, removing, or restructuring files.

Project Structure

ember is a flat Go package. All source files live in the repository root:

ember/
  ├── orm.go           # Package doc + Version constant
  ├── db.go            # Core DB struct — master + replica
  ├── builder.go       # Fluent SQL builder
  ├── model.go         # Active-record model layer
  ├── schema.go        # Struct introspection
  ├── dialect.go       # Dialect interface + implementations
  ├── blueprint.go     # Migration column/table DSL
  ├── migration.go     # Migration framework
  ├── raw.go           # RawQuery execution
  ├── tx.go            # Transaction wrapper
  ├── errors.go        # Sentinel errors
  ├── config.go        # Config structs
  ├── manager.go       # Connection manager
  ├── relations.go     # Eager loading engine
  ├── pagination.go    # Paginator
  ├── serialization.go # Serialization functions
  ├── events.go        # Observer event system
  ├── scopes.go        # Scope registry
  ├── macros.go        # Builder macros
  ├── casting.go       # Attribute casting
  ├── orm_test.go      # Integration tests
  └── go.mod           # Module definition

Pull Request Workflow

Before Opening a PR

  1. Ensure all tests pass: go test -count=1 -race ./...
  2. Run go vet ./... to catch common issues.
  3. Run golangci-lint run ./... (or at minimum gofmt -s -d .).
  4. Rebase onto the latest main branch: git rebase main.
  5. Write a clear, descriptive commit message (see conventions below).

PR Checklist

  • Does the PR add new exported symbols? If so, are they documented?
  • Does the PR add new functionality? If so, are there tests?
  • Does the PR fix a bug? If so, is there a regression test?
  • Does the PR change behavior? If so, is Project.md updated?
  • Do all CI checks pass (tests, lint, vet)?

Review Process

  • Maintainers will review your PR within a few days.
  • Address review feedback with additional commits (no squashing until merge).
  • Once approved, a maintainer will squash-merge your PR.
  • After merge, update any related documentation or examples in a follow-up.

Commit Message Conventions

We follow Conventional Commits format:

<type>(<scope>): <description>

[optional body]

[optional footer]

Types

TypeUsage
featA new feature
fixA bug fix
docsDocumentation only changes
styleFormatting, missing semicolons, etc. (no code change)
refactorCode change that neither fixes a bug nor adds a feature
testAdding or correcting tests
choreBuild process or tooling changes
perfPerformance improvement

Scope

Optional. Use the filename without extension: builder, model, dialect, migration, etc.

Examples

feat(builder): add WhereIn support for slices

fix(model): respect OwnerKey in LoadBelongsTo

docs: add contributing guide

refactor(dialect): split PostgresDialect into own file

test: add regression test for NULL scan in SQLite

Issue Templates Guidance

Bug Reports

When filing a bug report, include:

  • Go version — output of go version
  • ember version — the Version constant or commit hash
  • Database driver — SQLite3, PostgreSQL, or MySQL
  • Minimal reproduction — a self-contained code snippet that demonstrates the issue
  • Expected vs actual behavior
  • Full error output — include the stack trace if panicking

Feature Requests

When requesting a feature, include:

  • Use case — what problem are you trying to solve?
  • Proposed API — how should the feature look from the caller's perspective?
  • Alternatives considered — have you tried workarounds?
  • Example — a code snippet showing the desired usage

Questions & Discussions

For questions about usage, configuration, or best practices, check the FAQ first, then open a GitHub Discussion.
