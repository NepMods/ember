What databases does ember support?

ember supports three databases out of the box:

  • PostgreSQL — via lib/pq or pgx driver. Quoting with "identifier", $N placeholders, supports RETURNING and full ON CONFLICT DO UPDATE UPSERT.
  • MySQL — via go-sql-driver/mysql. Quoting with `identifier`, ? placeholders, ON DUPLICATE KEY UPDATE UPSERT.
  • SQLite3 — via mattn/go-sqlite3. Quoting with "identifier", ? placeholders, supports RETURNING (3.35+), ON CONFLICT UPSERT.

Additional databases can be added by implementing the Dialect interface and registering in GetDialect().

How does ember compare with GORM, Bun, or Ent?

See the detailed comparison page for a full breakdown. Key differentiators:

  • Flat package — No sub-packages, no import chains. One import ember "..." for everything.
  • Laravel Eloquent inspiration — Familiar API for developers coming from Laravel/PHP.
  • Master/replica routing — Built-in read/write splitting, not available in GORM without middleware.
  • ~3,000 LOC — Significantly smaller than GORM (~30k LOC) or Ent (~100k LOC with codegen).
  • Tag-based everything — Relationships, casting, columns all use struct tags. No verbose method chaining.
Is ember thread-safe?

Thread safety varies by component:

ComponentSafe?
DB (master + replicas)Yes — *sql.DB is safe, replica index uses atomic.AddUint64
ConnectionManagerYes — sync.RWMutex on all operations
EventDispatcherYes — sync.RWMutex on observe/fire
ScopeRegistryYes — sync.RWMutex on add/get
Schema cacheYes — sync.RWMutex, read-locked on fast path
Global macrosYes — sync.RWMutex on add/call
BuilderNo — single-goroutine only. Clone for parallel branches.
ModelDBNo — inherits Builder's lack of safety.
Does ember support connection pooling?

Yes. The PoolConfig struct exposes all database/sql pool settings:

db, err := ember.Open(ember.Config{
    Driver: "postgres",
    Master: "postgres://user:pass@localhost/mydb",
    Pool: ember.PoolConfig{
        MaxOpenConns:    25,
        MaxIdleConns:    10,
        ConnMaxLifetime: 5 * time.Minute,
    },
})

Pool settings apply to both master and replica *sql.DB handles. Go's database/sql manages the underlying connection pool transparently.

Does ember support database migrations?

Yes. ember includes a complete migration framework with a cross-dialect schema builder:

  • Define migrations by implementing the Migration interface (Version(), Up(), Down()).
  • Use Blueprint for type-safe column definitions: t.ID(), t.String("name"), t.Timestamps(), t.SoftDeletes(), etc.
  • Run/rollback/fresh through Migrator.Run(), Migrator.Rollback(), Migrator.Fresh().
  • Check status with Migrator.Status() and Migrator.Pending().
  • Supports foreign keys, indexes, custom column types, and raw DDL.
How does eager loading prevent N+1 queries?

ember uses a two-query approach instead of JOINs:

  1. Query 1: SELECT * FROM users — fetch parent records.
  2. For each relation, collect parent keys and execute one query: SELECT * FROM posts WHERE user_id IN (1, 2, 3, ...).
  3. Results are grouped in memory by foreign key and assigned to parent struct fields via reflection.

This produces two simple queries instead of one complex JOIN, avoids row duplication from join fan-out, works correctly with LIMIT, and is easier to debug in database logs.

Does ember support transactions?

Yes, with two patterns:

// Auto-rollback on error
err := db.Transaction(ctx, func(tx *ember.Tx) error {
    tx.Table("accounts").Decrement(ctx, "balance", 100)
    tx.Table("accounts").Increment(ctx, "balance", 100)
    return nil
})

// Manual with savepoints
tx, _ := db.Begin(ctx, nil)
tx.Savepoint(ctx, "sp1")
// ... operations ...
tx.RollbackTo(ctx, "sp1")
tx.Commit()

Transaction methods support Builder, ModelDB, and RawQuery within the transaction scope. The helper Transaction() is panic-safe — deferred recovery rolls back and re-panics.

Can I use raw SQL with ember?

Yes. The RawQuery type supports full raw SQL execution:

// Single row
var user User
db.Raw("SELECT * FROM users WHERE id = ?", 1).First(ctx, &user)

// Multiple rows
var users []User
db.Raw("SELECT * FROM users WHERE age > ?", 18).Scan(ctx, &users)

// Exec with result
result, _ := db.Raw("UPDATE users SET status = ?", "active").Exec(ctx)

// Get affected rows
count, _ := db.Raw("DELETE FROM users WHERE status = ?", "deleted").ExecAffected(ctx)

// Single column
var emails []string
db.Raw("SELECT email FROM users").Pluck(ctx, &emails)

// Single value
var count int64
db.Raw("SELECT COUNT(*) FROM users").Value(ctx, &count)
Does ember support soft deletes?

Yes. If a model has a deleted_at field (type *time.Time with tag ember:"nullable"), ember automatically enables soft deletes:

  • Delete() sets deleted_at to the current time instead of removing the row.
  • ForceDelete() permanently removes the record.
  • Restore() clears deleted_at.
  • All SELECT queries automatically include WHERE deleted_at IS NULL via SoftDeleteScope.
  • Use WithTrashedScope() to include soft-deleted records, or OnlyTrashedScope() to fetch only deleted records.
How do I define model relationships?

Relationships are declared using ember struct tags on the model fields:

type User struct {
    ID      int64   `ember:"primaryKey;autoIncr"`
    Name    string
    Posts   []Post  `ember:"relation:hasMany;foreignKey:user_id;localKey:id"`
    Profile Profile `ember:"relation:hasOne;foreignKey:user_id;localKey:id"`
}

type Post struct {
    ID     int64  `ember:"primaryKey;autoIncr"`
    UserID int64  `ember:"column:user_id"`
    Author User   `ember:"relation:belongsTo;foreignKey:user_id;ownerKey:id"`
    Tags   []Tag  `ember:"relation:belongsToMany;pivot:post_tags;pivotFK:post_id;pivotRK:tag_id"`
}

Supported relation types: hasMany, hasOne, belongsTo, belongsToMany. Relations can be loaded eagerly via With() or individually via LoadHasMany()/LoadHasOne()/LoadBelongsTo()/LoadBelongsToMany().

Is there pagination support?

Yes. The Paginate() method works on both Builder and ModelDB:

var page []Product
paginator, err := db.Table("products").
    Where("status", "=", "active").
    OrderBy("id", "ASC").
    Paginate(ctx, &page, 1, 20)

fmt.Printf("Page %d of %d (total: %d)\n",
    paginator.CurrentPage, paginator.LastPage, paginator.Total)

The paginator runs COUNT(*) first, then SELECT ... LIMIT/OFFSET. This approach is database-agnostic and avoids the deprecated MySQL SQL_CALC_FOUND_ROWS. Metadata includes CurrentPage, LastPage, PerPage, Total, From, and To.

Can I use multiple database connections?

Yes. The ConnectionManager provides a thread-safe registry of named *DB connections:

mgr := ember.NewConnectionManager()
mgr.Add("default", defaultConfig)
mgr.Add("reporting", reportingConfig)
mgr.Add("archive", archiveConfig)

// Switch between connections
db := mgr.Connection("reporting")
db.Table("sales").Get(ctx, &results)

// Close all connections
mgr.CloseAll()

The connection manager supports Add(), Remove(), Connection(), ConnectionSafe(), SetDefault(), Names(), and CloseAll(). All operations are protected by sync.RWMutex.

How does the event/hook system work?

ember has two complementary event systems:

1. Observer Pattern (EventDispatcher):

dispatcher := ember.NewEventDispatcher()
dispatcher.Observe(&User{}, &AuditObserver{})
dispatcher.ObserveAll(&GlobalObserver{})
db.SetEventDispatcher(dispatcher)

2. Hook Interfaces (per-model):

func (u *User) BeforeCreate(ctx context.Context) error {
    if u.Name == "" { return fmt.Errorf("name required") }
    return nil
}

Available hooks: BeforeCreate, AfterCreate, BeforeSave, AfterSave, BeforeUpdate, AfterUpdate, BeforeDelete, AfterDelete. The event lifecycle order is deterministic: Saving → Creating → BeforeSave → BeforeCreate → SQL → AfterCreate → AfterSave → Created → Saved (for creates).

How does attribute casting work?

Attribute casting is defined via struct tags. Casting is applied automatically on both read (from DB → struct) and write (struct → DB):

type Product struct {
    ID       int64                  `ember:"primaryKey;autoIncr"`
    Metadata map[string]interface{} `ember:"cast:json"`
    Price    float64                `ember:"cast:float"`
    IsActive bool                   `ember:"cast:bool"`
    Birthday time.Time              `ember:"cast:date"`
    CreatedAt time.Time             `ember:"cast:datetime"`
}

Supported cast types: json, string, int, float, bool, date, datetime. JSON fields are automatically marshaled/unmarshaled. Date fields use the configured format (default RFC3339).

How does master/replica routing work?

The DB struct manages one master *sql.DB and N replica *sql.DB handles:

  • Writes (INSERT, UPDATE, DELETE, DDL) always go to the master connection.
  • Reads (SELECT) are load-balanced across replicas using round-robin via atomic.AddUint64.
  • Sticky reads: Use ember.WithStickyMaster(ctx) to force reads to master after a write, ensuring read-your-writes consistency.
  • FOR UPDATE: Queries with lock modes (LockForUpdate(), SharedLock()) always route to master.
  • If no replicas are configured, all reads go to master.
Can I extend the query builder with custom methods?

Yes, through the macro system. Macros can be per-instance or global:

// Per-instance macro
builder := db.Table("users")
builder.Macro("whereActive", func(b *ember.Builder, args ...interface{}) interface{} {
    return b.Where("status", "=", "active")
})
result, err := builder.Call("whereActive")
if err != nil {
    log.Fatalf("macro call failed: %v", err)
}
if b, ok := result.(*ember.Builder); ok {
    b.Get(ctx, &users)
}

// Global macro (available on all builders)
ember.AddBuilderMacro("activeOnly", func(b *ember.Builder, args ...interface{}) interface{} {
    return b.Where("status", "=", "active")
})
result, err = db.Table("products").Call("activeOnly")
if err != nil {
    log.Fatalf("macro call failed: %v", err)
}
if b, ok := result.(*ember.Builder); ok {
    b.Get(ctx, &products)
}

Global macros are thread-safe (sync.RWMutex). Per-instance macros are local to a specific Builder. The Call() method falls back from instance macros to global macros.

Does ember have global scopes?

Yes. Global scopes are reusable query constraints registered per model type via the ScopeRegistry:

// Define scope
func ActiveOnly(b *ember.Builder) *ember.Builder {
    return b.Where("status", "=", "active")
}

// Register as global scope
db.ScopeRegistry().Add(&Product{}, ActiveOnly)

// Now ALL Product queries automatically include WHERE status = 'active'
db.Model().All(ctx, &products)  // includes scope
db.Model().Find(ctx, &product, 1)  // includes scope

Built-in scopes: ActiveScope, SoftDeleteScope, WithTrashedScope(), OnlyTrashedScope(). Scopes can also be applied directly via ember.ApplyScopes().

What is ember's testing strategy?

All integration tests use SQLite in-memory (:memory:) — zero setup, fast, deterministic. Tests run in approximately 1–3 seconds with no external database daemon required.

  • Dialect-specific SQL is tested via ToSQL() output comparison.
  • All three dialects are tested in blueprint schema generation.
  • Tests use the ember_test external package to exercise the public API as a real consumer.
  • Tests cover: CRUD, queries, transactions, migrations, relationships, eager loading, pagination, serialization, events, scopes, macros, casting, connection manager, and raw SQL.
Is ember production-ready?

ember v2.0.0 is a stable, documented, and tested release with full CI pipelines. However, consider these factors:

  • Test coverage: Comprehensive (100+ test cases) but SQLite-only. No PostgreSQL/MySQL integration tests in CI.
  • Community: Single-contributor project. Response times depend on maintainer availability.
  • Ecosystem: No third-party plugins, no code generation tooling, no model factories yet.
  • Performance: ~3,000 LOC flat package is lean. Builder is not safe for concurrent use. Schema introspection is cached with sync.RWMutex.
  • Migration safety: The migration DSL supports Up/Down/Fresh, but there is no dry-run mode or automatic backup.

It is suitable for small-to-medium projects, APIs, and internal tools. For high-throughput or multi-team projects, evaluate against GORM or Ent.

How do I serialize models to JSON?

ember provides standalone serialization functions:

// Single model to JSON
jsonBytes, err := ember.ToJSON(user)

// Collection to JSON
jsonBytes, err = ember.CollectionToJSON(users)

// Single model to map
m, err := ember.ModelToMap(user)

// Collection to maps
maps, err := ember.CollectionToMap(users)

// With custom config
cfg := &ember.SerializationConfig{
    DateFormat:        "2006-01-02",
    DateTimeFormat:    "2006-01-02 15:04:05",
    IncludeTimestamps: false,
    IncludeSoftDelete: false,
}
m, err := ember.ModelToMapWithConfig(user, cfg)

Serialization respects casting: JSON columns are unmarshaled into map[string]interface{}, dates are formatted according to config, and timestamps/soft-delete fields can be filtered. The FillFromMap() function reverses the process, populating a struct from a column→value map.
