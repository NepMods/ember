Architecture

ember is a single flat Go package (~3,000 LOC) providing a Laravel Eloquent-inspired ORM. This page documents the logical architecture, module relationships, data flows, and key design decisions.

Package Structure

ember is a flat package — every file shares all types and functions without import edges. This avoids circular imports and simplifies the user import path to one line.

ember/ ├── orm.go // Package doc + Version constant ├── db.go // Core DB struct — master + replica handles, Open(), routing ├── builder.go // Fluent SQL builder — ~1,500 lines, all query types ├── model.go // ModelDB — active-record CRUD, hook interfaces, scopes ├── schema.go // Struct introspection — ParseSchema, FieldSchema, ModelSchema ├── dialect.go // Dialect interface + Postgres/MySQL/SQLite implementations ├── blueprint.go // Migration column/table DSL — ColumnDef, IndexDef, ForeignKeyDef ├── migration.go // Migration framework — Schema, Migrator, Run/Rollback/Fresh ├── raw.go // RawQuery — raw SQL with Scan/First/Exec/Pluck/Value ├── tx.go // Tx — transaction wrapper with savepoints ├── errors.go // Sentinel errors + QueryError wrapper ├── config.go // Config and PoolConfig structs ├── manager.go // ConnectionManager — named connection registry ├── relations.go // Eager loading engine — HasMany/HasOne/BelongsTo/BelongsToMany ├── pagination.go // Paginator — COUNT + SELECT with metadata ├── serialization.go// ModelToMap, ToJSON, Collection serialization ├── events.go // Observer-pattern event system ├── scopes.go // ScopeRegistry — per-model global scope storage ├── macros.go // Builder macros — per-instance and global ├── casting.go // Attribute casting on read/write └── orm_test.go // Integration tests (SQLite in-memory)

Design Decisions

1. Flat Package (No Sub-Packages)

ember lives entirely in a single Go package. This avoids circular import problems common in layered ORMs, simplifies the import path to one line, and allows internal types to remain unexported while shared across all subsystems. The tradeoff is a larger API surface but zero import-cycle headaches.

2. Master/Replica Pattern

Each Config defines one master DSN and N replica DSNs. Writes always go to master; SELECTs use round-robin load balancing across replicas. A sticky-read context key (WithStickyMaster) forces reads to master after a write. This mirrors production deployment patterns and avoids middleware-level read/write splitting.

3. Interface-Based Dialect System

The Dialect interface abstracts quoting (" vs `), placeholders ($N vs ?), RETURNING support, and UPSERT syntax. New databases are added by implementing this interface and registering in GetDialect().

4. Eager Loading Uses IN Queries Instead of Joins

When loading HasMany/BelongsTo/BelongsToMany, ember first queries parent records, collects their keys, then executes a single WHERE fk IN (...) for all children. Results are grouped in memory by foreign key and assigned via reflection. This produces two simple queries instead of one complex join, avoids row duplication, and works correctly with LIMIT.

5. Pagination: Separate COUNT + SELECT

Paginate() runs COUNT(*) first, then SELECT ... LIMIT/OFFSET. Database-agnostic, avoids deprecated MySQL-specific SQL_CALC_FOUND_ROWS.

6. Tag-Based Casting

Attribute casts are declared on struct field tags (ember:"cast:json") rather than via a method. Keeps the type system as the source of truth and makes casts visible at a glance.

7. Observer Pattern for Events

The Observer interface + EventDispatcher with Fire() broadcasting follows the classical Observer pattern. Synchronous, deterministic, and simpler to debug than channel-based approaches.

8. Global Scopes via Registry

Scopes are registered imperatively (db.ScopeRegistry().Add(&MyModel{}, scope)) rather than via a boot() method. Decouples scope definition from model definition and allows runtime registration.

9. Schema Caching with sync.RWMutex

ParseSchema() caches parsed schemas by reflect.Type in a global map guarded by sync.RWMutex. Reads use RLock for fast-path; write lock only acquired when a new type is parsed.

Security Considerations

SQL Injection Prevention

  • All user values are passed as bind parameters (? or $N), never interpolated into SQL strings.
  • Column/table names are quoted via Dialect.QuoteIdentifier() — they come from struct tags or trusted code, not user input.
  • Operator whitelist: Builder.Where() validates the operator against a map of valid operators. Invalid operators silently default to =.
  • Raw SQL methods (WhereRaw, HavingRaw, OrderByRaw, RawQuery) accept raw SQL — the caller is responsible for safe SQL.

Input Validation

  • Savepoint names validated with ^[a-zA-Z_][a-zA-Z0-9_]*$ before interpolation.
  • Default() quoting: String values are escaped (' → '') and wrapped in single quotes.
  • Batch INSERT validation: All rows must have the same column set; mismatched columns return an error.

Known Limitations

  • Pluralization is English-only — the pluralize() function handles common irregulars but does not support other languages.
  • No model factory support — unlike Laravel's Factory for test data generation.
  • No polymorphic relationship test coverage — MorphOne, MorphMany, MorphTo are parsed but not exercised in tests or eager loading.
  • No Postgres/MySQL integration tests — all tests use SQLite in-memory. Dialect-specific features are tested via ToSQL() output.
  • Concurrent builder use is not safe — sharing a Builder across goroutines causes data races.
  • Embedded/anonymous struct fields are skipped — ParseSchema skips anonymous fields.
  • No migration file scanning — migrations must be registered explicitly with NewMigrator(db, migrations...).
